Section 2Load profile — mean vs. burst

Averages mislead. PACS load is bursty, and sizing is done against the burst, not the mean. The ~20 ev/s quoted above is the average of the peak hour (0.02 ev/s per device = the midpoint of a 30–70 s cadence).

Burst-to-mean ≈ 20× (worst-case alarm storm) — this is the number to size against. JetStream absorbs the burst (durable buffer, no loss); audit drains it at the ceiling rate, so a burst produces latency, not loss. The sizing metric: how many devices a tier can carry such that a worst-case alarm storm (~2 events per device) drains within a target latency T ⇒ N_burst(T) ≈ ceiling × T / 2.
Section 3Vertical scaling — active devices per hardware class

Two independent limits: A) audit throughput (concurrency × 1/DB-latency) and B) resident RAM plus practical factors (~0.02–0.05 MB per active device on the adapter; plus the unmeasured ones: device-tree build at startup, NATS subscriptions, UI).

Key point: the mean (0.02 ev/s per device) is not the limit on any tier — the ceiling sits ~10–50× above it. What decides is the burst: sizing to drain a worst-case alarm storm within a target latency (see §2). The declared device counts are conservative and support-bound, far below the throughput/burst ceiling; going higher requires testing the practical factors (device-tree build, NATS subscriptions, UI), not throughput.

Section 4Declared configurations + a separate Postgres cluster

With a dedicated high-performance Postgres (dedicated NVMe / provisioned IOPS, its own CPU): (1) the DB-IO wall disappears → the ceiling becomes server-CPU-bound ≈ (cores − reserve) × ~180 ev/s; (2) the host is freed up (~300–450 MB RAM and ~0.66 core of DB); (3) Audit:MaxConcurrency must be raised to roughly the core count.

Section 6Horizontal scaling & load balancing

Vertical scaling (§1–5) ends at one Postgres primary (audit writes). Horizontal means more component instances behind a load balancer. What scales freely and what stays bound:

Key finding: horizontal scaling freely raises event generation (adapters), API/read/UI and audit-consumption parallelism — but audit writes converge on a single Postgres primary, whose write capacity is the horizontal ceiling for persistence. Beyond it you need DB sharding/partitioning (a large change). Horizontal scaling is therefore mainly about HA/redundancy, API throughput and burst absorption; the write ceiling is raised by a faster/separate Postgres (vertical, §4), not by the number of server instances.

Theoretical horizontal scaling

What adding server instances (behind the nginx LB) multiplies — and what stays flat:

Read/API/UI and event-consumption parallelism grow roughly linearly with the number of server instances; audit writes stay flat — every instance converges on 1 Postgres primary. Raising the write ceiling means a faster/separate Postgres (§4) or DB sharding/partitioning (a large change), not more server instances. The JetStream cluster absorbs bursts in the meantime; draining into the DB remains bound to the primary.

Scaling / balancing the database (beyond one primary)

Reads balance freely — read replicas plus a read/write split (audit queries and reporting on the replicas). Writes stay on a single primary; raising that ceiling can be done as follows (increasing difficulty):

#ApproachEffect on writesDifficulty / consequence
1Vertical primary (NVMe / provisioned IOPS / more cores)higher ceiling for one primary (≈ §4)small — no app change; up to a point
2Partition Audit (declarative, by time)cheaper inserts (smaller indexes) + retention = DROP partitionmedium — migration + partition key; also solves the no-TTL problem
3TimescaleDB hypertable for Audithigh append/ingest + native retention and compressionmedium — extension; strong fit (audit is time-series)
4Distributed Postgres (Citus) — sharded across N workers~linear write scaling (N nodes)large — shard key, reads via coordinator (scatter-gather)

Caution: the audit panel, reporting and ABAC associations currently assume a single logical database — sharding/Citus/Timescale change the query path and require app changes plus testing. Genuine write balancing (more than one primary) means sharding the data (#4/#5); a read replica does not raise the write ceiling. Pragmatic order: vertical primary (#1) → partitioning + retention (#2) → only then Citus/Timescale (#3/#4), if real volume outgrows one large primary.

Load balancing

  • nginx front door → an upstream pool of servers: REST least-conn / round-robin; WebSocket/SignalR sticky (ip_hash or cookie) — a connection stays on one instance (no backplane).
  • Adapters are not load-balanced — shard the devices (by range) across containers; each adapter owns its own set of connections.
  • NATS / Postgres: clients balance connections across the cluster, respectively a read/write split across primary and replicas.

Blockers before a multi-instance server (must fix)

  1. Correlation and Occupancy use durable consumers — with several instances the events would be split, breaking scenarios and the occupancy projection. They must run on a single instance / leader-elected / partitioned by entity.
  2. Live audit panel push is in-process (AuditStore→AuditCache) — with sharded audit each instance would push only its own share of events. This needs NATS-based audit push or a SignalR backplane.
  3. SignalR has no backplane — in-process broadcasts do not cross instances; WebSocket connections must be sticky at the LB.

A multi-instance server is not yet deployed or tested (the compose file is single-instance). The above are architectural assumptions — before scaling the server horizontally, the three blockers must be resolved (a candidate for its own ticket) and the real write ceiling of one Postgres primary measured. Adapters and the read/UI layer scale horizontally without these blockers.

Section 7Enterprise federation — isolated nests + a central Master

An alternative to scaling one global database: split the problem by location. Each site is an autonomous nest (its own PQ + Postgres + adapters) handling its devices, access, alarms and audit locally in real time. Audit and telemetry sync up to a central Master in batches, off-peak (at night), optionally filtered; configuration (people / permissions / policies) flows down from the Master.

DataDirectionMode
Config — people, permissions, policies, device catalogMaster → nestspush (near real-time)
Audit / events / telemetrynests → Masterbatched, off-peak (night), filtered
Access decisions, alarms, I/Olocally in the nestreal-time, autonomous

Why this fits PQ / physical security:

  • The write ceiling disappears for real-time work — each nest carries only its own load (~20 ev/s peak) → a Small/Medium node suffices, no DB sharding.
  • Autonomy / HA — a nest keeps working through a WAN outage; access and alarms must not fail when the link to headquarters is lost.
  • The Master never sees a real-time burst — only the nightly batch → even a modest Master handles the aggregate of many nests.
  • Filtering / aggregation — only security-relevant events go to the Master (access/alarm/tamper), not every video motion → the volume reaching the Master is orders of magnitude below the sum of raw events.
  • Natural isolation (data residency, blast radius, multi-tenancy).
Open questions (a new capability — PQ has no federation/sync today):
  • Identity: events and audit rows carry v7 GUIDs → globally unique, idempotent upsert on the Master ✓. Entities (people/devices) need globally unique IDs or per-nest namespacing — the main modeling question.
  • Consistency: the Master is eventually consistent (up to ~1 day) → good for reporting/archive/compliance, not for live central supervision. A live SOC across sites would need a live stream (e.g. JetStream source/mirror) alongside the nightly batch.
  • Transport: watermark-based export (sequence/time) + COPY to the Master, or JetStream source/mirror, or filtered logical replication.

vs. DB sharding (§6): federation splits the problem by location — each nest stays small (no Citus/Timescale needed) and the Master only handles the off-peak aggregate. For multi-site physical security this is generally a better and more autonomous pattern than sharding one global real-time database. It is how enterprise PACS scale as well (federated sites + headquarters).

The Master is batch, not streaming: the nightly sync is a bulk COPY of filtered audit rows (bypassing the per-event AuditStore pipeline), hence ~100k rows/s ≫ the ~6k streaming ceiling. The daily volume reaching the Master (aggregate of 10 nests, ~15% filter) is on the order of hundreds of thousands of rows per night → it completes in minutes; the Master is massively over-provisioned for batch work. (The ~6k streaming ceiling would only apply if the Master ingested per-event in real time — which is precisely what federation does not do.)

How to read this: throughput of ~60,000 ev/s is solid (10× the ceiling of a single XLarge, spread out — it never lands on one database). The active-device counts are throughput-derived upper estimates — "@ mean" (~3 M) is the theoretical maximum under average load, "burst-bound" (~900 k) is the sizing figure for peak bursts. In practice the unmeasured factors bind sooner (device-tree build at startup, number of NATS subscriptions, UI, working-set RAM) — expect a real operational count per nest in the thousands to low tens of thousands, not 90 k, until those factors are measured. Throughput is therefore not the limit on device count; practice is (a separate test).
SummaryConclusions and recommendations
  • Do not size against the mean. ~20 ev/s at 1,000 devices is the average of the peak hour; real load is bursty (~20× mean during an alarm storm after an outage). Sizing means draining the worst-case burst within a target latency T, not carrying the average.
  • Parallelizing the audit took 147 → 194 ev/s on WSL2 (DB-IO bound); in production, or on a separate Postgres, ~450 (Small) – 2,340 (Large), up to ~7,000 ev/s (XLarge, optimistic) — that is the headroom for bursts.
  • A separate Postgres cluster is recommended for Large / multi-site — it removes the only measured bottleneck (DB fsync) and frees the host.
  • Horizontal (§6): adapters, API/read/UI and state scale freely behind the nginx LB (WS sticky); audit writes, however, converge on 1 Postgres primary — the write ceiling is raised vertically, not by instance count. A multi-instance server has 3 blockers (single-instance correlation/occupancy, live-audit push, SignalR stickiness).
  • Enterprise / multi-site (§7): for many sites the cleanest option is to federate autonomous nests and sync audit to a central Master in filtered batches off-peak — this sidesteps the write ceiling without DB sharding and gives each site autonomy (even without WAN). A new capability; PQ does not have it today.
  • The declared counts (25 / 250 / 250+) are conservative — the hardware carries far more at a realistic peak; raising the declaration requires a separate test of the practical factors (device-tree build, NATS subscriptions, UI), not of throughput.
  • Retention/pruning of Audit is mandatory on every tier (~0.2 GB/day at peak, 2–25 GB/day at the ceiling, no TTL). The licensing cap per device category (e.g. CctvCamera) is a separate commercial lever.
Basis and limits of the model. This is an extrapolation from a single measurement point (194 ev/s @ 1.08 core, WSL2 all-in-one). The figures in sections 2–5 are estimates under the stated assumptions and need to be confirmed by measurement on the target hardware, ideally with a separate Postgres. Burst-to-mean ≈ 20× and ~2 events per device in an alarm storm are engineering estimates — replace them with the profile of your own installation; the formula N_burst(T) = ceiling × T / events_per_device holds for any values. Unmeasured and out of scope: device-tree build at startup, NATS subscription scaling, UI rendering, multi-adapter and HA topologies — these likely bind before throughput at very high device counts.
