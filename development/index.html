Developer guide

Enable local development

PQ keeps its internal services — the NATS message bus and the /Internal/* API — behind the Docker Compose perimeter. When you run an adapter on your own machine (Visual Studio or Rider) instead of inside Compose, that perimeter has to be opened up for it. This guide walks through doing that, safely and reversibly, for both a repo checkout and a bare installed box.

Two paths · repo checkout or installed box Reversible — turn it back off when you're done

What development mode is

The trust boundary you're temporarily moving.

Per ADR-0007, adapters running inside the Docker Compose perimeter are treated as part of the trusted computing base: network isolation — not per-adapter authentication — is what keeps NATS and the /Internal/* API safe. A host-run adapter sits outside that perimeter, so development mode deliberately punches two holes in it: it publishes NATS on a reachable port, and (if needed) lets your host call /Internal/*. Both are meant to be temporary and are easy to reverse — see Turn it off below.

Never enable this in production.

The nats-dev proxy publishes NATS on 0.0.0.0 — reachable from anywhere on the LAN — using the shared pq-master / pq-master credentials. InternalApi__AllowExternal, if you ever need it, bypasses the IP-based protection in front of /Internal/*. Only do this on a development box you control.

PQ NuGet feed

Your adapter project references Pq.Adapters.Framework from the Protequ package registry.

The framework package is published to a private NuGet feed on repo.protequ.com. The feed requires authentication even for reads. You'll receive a personal account (username + token) from Protequ — add the feed once with those credentials:

dotnet nuget add source https://repo.protequ.com/api/packages/PQ/nuget/index.json \ -n pq -u <your-username> -p <your-token> \ --store-password-in-clear-text

Replace <your-username> / <your-token> with the credentials you received from Protequ. On Windows you can drop --store-password-in-clear-text — the password is then stored DPAPI-encrypted in your user-level NuGet.Config. On Linux/macOS the flag is required. The account is read-only; publishing goes through CI.

Branch A — I have the repo

You have a checkout with .install/compose and can bring the stack up yourself.

1

Start PQ with the dev profile

From the compose folder, bring the stack up with the dev profile and allow external Internal API access:

cd .install/compose INTERNAL_API_ALLOW_EXTERNAL=true docker compose --profile dev up -d

This starts the nats-dev socat sidecar, which publishes NATS on localhost:4222, and sets InternalApi__AllowExternal=true so your host can call /Internal/*.

2

Configure your adapter

Run the helper script from the repo root:

.\setup-adapter-dev-config.ps1

It writes ~/.pq/adapter-dev.json with the NATS connection (localhost:4222, pq-master / pq-master), read as a fallback by AdapterFramework.ApplyMqFallbackConfiguration for any locally-run adapter without its own complete Mq config, and sets OTEL_EXPORTER_OTLP_ENDPOINT so adapter logs flow to Grafana.

Branch B — I only have an installed box

No repo checkout — just a running PQ install reachable at its front door.

1

Publish NATS

Run a standalone socat sidecar on the Docker host to publish NATS on 4222:

docker run -d --name nats-dev --network pq_default -p 4222:4222 alpine/socat:latest TCP-LISTEN:4222,fork,reuseaddr TCP:nats:4222

This does not survive a redeploy.

A standalone docker run container isn't part of the compose stack, so docker compose down — or any redeploy — doesn't restart it. Re-run the command above afterwards. It publishes NATS on 0.0.0.0 (LAN-reachable) with the shared pq-master / pq-master credentials.

2

Internal API

Normally, nothing to do here. Your host-run adapter reaches /Internal/* through the nginx front door at https://localhost:5443, using the base URL and X-Api-Key it receives automatically at registration. The adapter's HTTP client bypasses TLS validation for this, so there's no CA setup either. On a standard installed box, /Internal/* is not IP-blocked from the host.

Only if you hit an HTTP 403 on /Internal/* (see Troubleshooting below) does an admin need to set InternalApi__AllowExternal=true on the server service and restart it.

3

Configure your adapter

There's no repo checkout to run the setup script from, so hand-write ~/.pq/adapter-dev.json:

{ "Mq": { "Host": "localhost:4222", "User": "pq-master", "Password": "pq-master" } }

Then set OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317 as a persistent user environment variable, so adapter logs flow to Grafana.

Run & verify

Start your adapter from Visual Studio / Rider and confirm it's actually talking to PQ.

1

Adapter connects to NATS

Your adapter connects to localhost:4222. A plain TCP connect to that port should return a NATS INFO {…} banner — a quick sanity check that the sidecar is up before you even start the adapter.

2

Adapter registers with the server

Look for AdapterConfigurationResponse in your adapter's logs — that confirms registration succeeded and it received its API base URL and key back from the server.

Observability

Your host-run adapter's logs and traces show up alongside everything else.

Set OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317 so your adapter exports to the Alloy collector, which is always running — no compose profile needed to turn it on. From there, logs appear in Grafana at https://localhost:5443/grafana/d/pq-home, behind the front door — not on localhost:3000.

Turn it off

Close both holes once you're done developing.

Branch A — stop the dev profile:

docker compose --profile dev down

Branch B — remove the standalone sidecar:

docker rm -f nats-dev

If you set InternalApi__AllowExternal=true as a troubleshooting fallback, unset it on the server service and restart the container.

Troubleshooting

Common issues and how to resolve them.

Connection refused to localhost:4222

The nats-dev sidecar isn't running. Branch A: confirm you started with --profile dev (docker compose ps should show nats-dev). Branch B: re-run the docker run --name nats-dev … command — remember it doesn't survive a redeploy.

403 Forbidden on /Internal/*

Set InternalApi__AllowExternal=true on the server service and restart it. On a repo checkout, this is the same environment variable you can pass to docker compose --profile dev up -d.

Adapter not receiving commands

Check the NATS connection in your adapter's logs, confirm it registered successfully (look for AdapterConfigurationResponse), and confirm the device is started in the PQ UI.
